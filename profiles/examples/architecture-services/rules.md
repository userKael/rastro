# Example profile: services architecture rules

A starting point for a team that builds a service in layers. It is an example, not doctrine. Copy the rules you keep into the `## Non-negotiable rules` section of your `AGENTS.md`, rewrite each `Why here:` line with a consequence real in your codebase, and delete the rest. Skills cite a rule by its ID, so keep the IDs you adopt.

The examples use a bookstore with three modules: `catalog`, `orders` and `inventory`. The `Why here:` lines describe that bookstore, not your service.

## Layers

| Layer | Holds | Calls |
|---|---|---|
| `handler` | an HTTP endpoint, a job or a queue consumer | one `service` |
| `service` | one business operation per entry point | other services, a `repository`, an external client |
| `repository` | reads and writes of one persistence store | the store |
| `domain` | optional; entities and value objects with their invariants | nothing outside itself |

Set `architecture.layers` in `.rastro/config.yml` to the layers you use, and `architecture.modules` to your module names. An external client sits beside the repository: a service reaches a system outside the process only through one of the two.

## Rules

- **[module-public-api]** A module imports another only through its public API.
  **Symptom:** an import of `<other-module>/internal/...`, or of any path outside `<other-module>/index.ts`. Example: `orders` importing `catalog/internal/price-table`.
  **Why here:** `catalog` can no longer move or rename a file without checking every module that reaches into it, so its internals stop being private.
  **Ask the author:** import the type or function from the module's `index.ts`. When the symbol is not exported there, ask the owning module to export it; do not copy it.

- **[no-service-cycle]** Services may call each other, and a dependency cycle between services is forbidden. Without a cycle detector in the lint this rule is advisory: a reviewer sees only the cycles that fit in the diff.
  **Symptom:** service A depends on service B and B depends on A, directly or through a chain. Example: `OrderService` reserves copies through `Inventory`, and `Inventory` looks up open orders through `OrderService`.
  **Why here:** neither service can be constructed without the other, so each is tested only with the other present, and a change to one needs a review of both.
  **Ask the author:** name the edge to cut. Either move the shared step into a third service both depend on, or replace one direction with an event. See `golden-paths/creating-a-service.md` to wire the detector.

- **[pure-domain]** When a `domain/` exists, it imports no framework and no ORM.
  **Symptom:** an import of a web framework, an ORM or a dependency-injection container in a file under `domain/`, or a decorator from one of them on a domain class.
  **Why here:** `Order` carries the rule that an order has at least one line. With an ORM decorator on it, a table change becomes a domain change, and the rule cannot be tested without the ORM loaded.
  **Ask the author:** keep the domain class plain. Put the mapping between it and the persistence entity in the repository.
  **Known debt:** <files under `domain/` that already import a framework or an ORM; delete this line when there are none>.

- **[no-sensitive-log]** Never log data of a class listed in `architecture.sensitive_data`.
  **Symptom:** a log call, an error message or a trace attribute that carries a sensitive field, or an object that contains one. Example: `logger.info({ customer })` where `customer` holds an email address.
  **Why here:** a log leaves the service. A log store has its own readers and its own retention, and neither is the database's. In the bookstore, `sensitive_data` is `[customer email, shipping address, session token]`.
  **Ask the author:** log the identifier (`orderId`) instead of the object. Name the class from `architecture.sensitive_data` that the line exposes.

- **[migration-via-tool]** A migration is generated by the migration tool and always has a reversal.
  **Symptom:** a migration file written by hand, with no tool command that produced it; a migration with no reversal; a reversal that does not undo exactly what the forward step did.
  **Why here:** the tool tracks the model. A hand-written migration drifts from it, and the next generated migration either repeats the drift or contradicts it. Without a reversal, rolling back a deploy leaves the schema ahead of the code.
  **Ask the author:** regenerate the migration with the tool, as in `golden-paths/creating-a-migration.md`, and state the command in the PR description. Add a reversal that undoes the forward step and nothing more.

## Known debt

A `Known debt:` line lists files that already break the rule. It is not precedent and it does not grow: a new file with the same defect is a blocking violation.
